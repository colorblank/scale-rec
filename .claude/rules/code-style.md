# Rust 代码规范

格式化与工具：严格使用 cargo fmt 进行自动格式化，无需手动调整缩进与行宽。代码质量检查使用 cargo clippy。
文档注释：
    模块级：每个 .rs 文件必须以 //! 开头，用一句中文简述文件职责。
    条目级：所有 pub 可见的 struct、enum、trait 和 fn 必须包含 /// 注释。Struct 采用“单行总结 + 空行 + 详细描述”的格式；构造器需说明参数约束；Trait 实现方法需描述当前实现的特定行为。
测试规范：单元测试放在文件底部的 #[cfg(test)] 模块中，测试函数命名需具备描述性（如 test_bucketing_above_range）。集成测试统一放在项目根目录的 tests/ 文件夹中，按类别划分文件。
命名约定：结构体、枚举及其变体采用 PascalCase；函数、方法、模块及变量采用 snake_case。

# Python 代码规范

工具链与配置：代码托管在 python/ 目录下，统一使用 uv 进行包管理，ruff 进行代码检查与格式化。
    常用命令：uvx ruff check（检查）、uvx ruff format（格式化）、uv run pytest（测试）。
    核心配置：行宽限制为 100 字符，字符串使用双引号。需在 pyproject.toml 中忽略 E402 规则，以兼容 PEP 257 关于模块文档字符串位于导入语句之前的规范。
文档字符串：
1. **格式与标点**：
   - 必须使用三重双引号 `"""` 包裹文档字符串。
   - 必须使用 **Google Style** 格式（包含 Args, Returns, Raises 等标准区块）。
   - 所有的描述性文字（总结、详细描述、参数说明）必须使用 **中文**。
   - 代码示例（Example）中的代码和变量名保持英文。
2. **模块级（文件开头）**：
   - 文件的第一行必须是 `from __future__ import annotations`。
   - 第二行必须紧跟模块级 Docstring，用一句话简述该文件的核心职责。
3. **类与函数级**：
   - **首行总结**：用一句精炼的中文概括功能，以句号结尾。
   - **详细描述**：如果逻辑复杂，空一行后补充详细解释、算法原理或注意事项。
   - **Args（参数）**：列出所有参数。格式为 `参数名 (类型): 描述`。如果已有 Type Hints，类型可省略，但建议保留以增强可读性。
   - **Returns（返回值）**：描述返回值的业务含义。如果返回 `None` 可省略。
   - **Raises（异常）**：必须列出函数内部主动抛出（raise）的所有异常及其触发条件。
   - **Example（示例）**：对于复杂的工具函数，提供一个简短的 `>>>` 交互式调用示例。
4. **禁忌**：
   - 禁止生成无意义的废话（如 `def get_name(): """获取名字"""`）。
   - 禁止在 Docstring 中使用单引号 `'''`。
   - 禁止遗漏 `Raises` 区块（如果有显式的异常抛出）。
5. 类型注释，函数的输入变量和返回值必须有类型注释。
6. 采用Pathlib管理路径
导入与命名：导入顺序严格遵循“标准库 → 第三方库 → 本地模块”，由 ruff 自动排序。类名使用 PascalCase，函数、变量及模块文件名使用 snake_case，常量使用 UPPER_CASE。

# 跨语言通用规则

特征定义同源：所有特征规格（名称、词表大小、嵌入维度）必须唯一来源于 FeatureDag（Rust 中的 embeddable_features() / Python 中的 feature_tuples()）。模型配置文件（YAML）及 ModelConfig 结构体/类中严禁重复定义特征。

测试与提交：
    测试要求：每个新增的公开结构体/类或重要方法都必须配备对应的单元测试或集成测试，冒烟测试需至少验证前向传播的输出形状。
    提交规范：遵循 Conventional Commits 规范，如 feat(feats): add ...、fix: correct ...、test: add ... 等。
